# 华为杯新手使用指南

本指南面向第一次参加华为杯/研究生数学建模类比赛、希望使用 MathModel Skill Standard 完成完整建模流程的用户。

它只调整 Agent 的执行方式与讲解方式，不改变 Standard 的 S0-S8 核心流程、证据门禁、真实计算要求或最终 Word/PDF 验收标准。

## 目标

新手模式遵循四个原则：

1. **先做可运行基线，再做增强。** 先建立一个能解释、能计算、能验证的基线模型，再根据结果增加更复杂的方法。
2. **每一步都解释“为什么”。** Agent 在关键阶段给出模型选择理由、输入输出、假设和下一步判断依据，而不是直接跳到代码或论文。
3. **真实运行优先。** 所有关键结论必须来自实际运行的代码、数据处理和结果文件，不允许用“理论上应该”替代计算结果。
4. **保留正式验收。** 新手模式不是简化版论文模式，S6 证据检查、S7 正式写作和 S8 Word/PDF 检查仍然保留。

## 推荐目录

在项目根目录准备：

```text
your-project/
├── .agents/skills/          # Codex；其他 Agent 使用各自目录
├── requirements.txt
└── problem_files/
    ├── 赛题.pdf
    └── 官方附件.xlsx
```

所有赛题代码、结果、图表、证据和论文仍写入 `paper_output/`。

## 推荐启动提示词

```text
请使用 $paper-workflow-orchestrator 完成这个数学建模项目。
赛题和官方附件已放在 problem_files/。

我是第一次参加华为杯，请按“新手引导但正式交付”的方式执行：

1. 先运行 preflight_check.py 和 workflow_guard.py --status，再按 S0-S8 推进，不跳阶段。
2. S1 先用通俗语言说明每一问在求什么、已知量/未知量是什么、最难的地方在哪里。
3. S2 对每一问先给出一个可运行的基线模型，再给出 1-2 个可能的增强方向；先完成基线，不要一开始堆复杂模型。
4. 每次决定模型、指标、参数或算法时，简要说明：为什么选它、需要什么输入、会产出什么、如何判断效果好坏。
5. S3-S5 必须真实编写并运行代码，结果、图表和表格写入 paper_output/，不要虚构计算结果。
6. 基线模型跑通后，再根据误差、残差、稳定性、约束满足情况或业务解释决定是否升级模型。
7. 如果多个模型都可行，至少比较精度、稳定性、可解释性和实现成本，不要只看单一指标。
8. 对关键假设、参数和结论做必要的敏感性/稳健性检查；如果数据不足，明确写出限制，不补造数据。
9. S6 evidence gate 使用 official 模式并保持输入哈希新鲜。
10. S7 仍按 Standard 正式主线完成完整章节写作、逐章审计、必要修复、合并和全文统一改写，不降低为短报告。
11. 只有 authoring PASS 后才生成 final_paper.docx，并用 LibreOffice 执行 --render required。
12. 任一门禁失败时继续修复；如果卡住，先告诉我“失败阶段、失败原因、下一步最小修复动作”，不要直接跳过。

每完成一个主要阶段，请额外给我一个不超过 8 行的“新手解释”：
- 这一阶段做了什么；
- 为什么这样做；
- 产生了哪些文件；
- 下一阶段要看什么。
```

## 建议的推进顺序

### S0-S1：先看懂题，不急着写代码

至少确认：

- 每一问的目标变量和评价标准；
- 官方附件中每张表、每列数据的含义；
- 哪些是硬约束，哪些是可调整假设；
- 各小问之间是否有结果依赖。

如果这些内容仍不清楚，不进入复杂建模。

### S2：先建立基线模型

基线模型应满足：

- 能完整跑通；
- 能解释变量和参数；
- 能给出一组可验证结果；
- 复杂度足够低，方便发现数据或代码问题。

只有当基线结果暴露出明确缺陷时，再升级模型。例如：明显非线性、残差结构明显、约束频繁被破坏、预测不稳定或目标函数表现不足。

### S3-S5：让代码成为证据

每个关键结果都应能追溯到：

```text
输入数据 -> 处理代码 -> 模型代码 -> 输出结果 -> 图表/表格 -> 论文结论
```

不要手工修改最终数字来“让结果更好看”。如果结果异常，优先检查数据、单位、边界条件、随机种子、求解器状态和评价指标。

### S6：验证结果是否真的可信

重点检查：

- 结果是否由当前版本代码真实产生；
- 关键数字是否能在结果文件中找到；
- 单位、量纲和统计口径是否一致；
- 图表与正文描述是否互相矛盾；
- 是否存在只在论文里出现、但没有计算证据的结论。

### S7-S8：最后再把它写成论文

论文写作应建立在已经通过计算和证据检查的结果上。正式稿至少要解释：

- 为什么建立这个模型；
- 模型假设和符号；
- 推导或算法过程；
- 参数来源；
- 实际计算结果；
- 结果解释；
- 优缺点与限制。

最后仍按 Standard 要求生成 Word，并进行 PDF 渲染检查。

## 卡住时的恢复提示词

```text
请使用 $paper-workflow-orchestrator 恢复这个项目。
先运行 workflow_guard.py --status，读取 workflow_guard_report.json、workflow_memory.json 和当前文件哈希。
我是新手，请从第一个失败阶段继续，并先解释：失败原因是什么、最小修复动作是什么、修复后如何验证。
不要重跑已经通过且哈希仍有效的阶段，也不要跳过 S6-S8。
```

## 什么时候不该继续加复杂模型

出现以下情况时，优先修复基础问题，而不是继续叠加算法：

- 输入数据还没有清洗清楚；
- 单位或变量定义不统一；
- 基线代码还不能稳定复现；
- 评价指标没有定义；
- 结果没有证据文件；
- 复杂模型的提升很小，但解释成本显著增加。

对于第一次参赛，**一个跑通、可解释、验证充分的模型通常比一个没有证据链的复杂模型更有价值**。
